# Council Review 17 - ADR-0045 Compliance and Capability Gating Follow-Up

Date: 2026-09-14
Branch: feature/fast-wins-ministry-formation-ui
Baseline: bff3392ddd454fb81066cf3315aa896db65c6a05 (diffed against main)
Scope: PR #105, second round of changes — full ADR-0045 role-scoped access (`ministry_formation_reviewer` role, faculty section-scoping, formation-advisor advisee-scoping, registrar cap, pastoral-notes restriction) and a new `ministryFormation` institution capability, per `docs/adr/0071-ministry-formation-reviewer-role-and-capability-gating.md`. Follow-up to Council Review 16 (revise, fixed in commit `5c61b6c`).
Decision Requested: ship / revise / defer / split / reject

## Executive Verdict

Decision: **revise**
Release status: not released; multiple confirmed runtime-breaking and privacy-breaking defects, none requiring a redesign to fix
Confidence: very high — the most severe findings were independently reproduced against a real local Postgres instance by three separate councilors, not inferred from reading code

This round shipped with 45/45 mock-DB tests green, clean lint, and a clean build — and is nonetheless broken in ways that would fail on first real use. Three councilors independently ran actual SQL against the real schema (not the mock) and found that the faculty-scoping query references tables and columns that do not exist (`academy_registrations`/`instructor_person_id` instead of the real `academy_course_section_registrations`/`primary_instructor_id`), that the reviewer-grant INSERT violates NOT NULL constraints and targets a nonexistent unique index, and that the FK-restrict migration drops constraint names Postgres never actually generated. Two more councilors independently found, and one live-reproduced with real pastoral content, that `canSeePastoralNotes()` lets a registrar who also holds the new reviewer role see pastoral notes (contradicting the ADR's own explicit claim), and that `getStudentFormationRecord()` has no deny-fallback for `academic_admin`, granting it fully unscoped tenant-wide read access. None of this was caught by the test suite, because the module's established mock-DB testing pattern validates against a hand-maintained fake query responder, not the real schema — a blind spot that let fabricated table/column/constraint names ship with full green tests.

This is not an architectural rejection. Every defect below has a small, bounded fix. But it cannot ship as committed, and the fix pass needs to verify against the real local database this time, not just the mock.

## Council Role Findings

### Product and Market Councilor

Capability defaults and API/page-level enforcement are real (verified server-side re-checks, not just UI hiding). The reviewer grant/revoke control on the staff page is a genuine, usable admin capability with confirmation and error handling. Found that admin-side nav (`admin-shell.tsx`) never got capability-aware hiding — only the student PWA did — so an institution_admin at a children's school still sees "Ministry Formation" in the sidebar and lands on a ghost page; ADR-0071's Consequences section overstates this as tenant-wide when the Decision section correctly scoped it to the Student PWA only. Also noted this round executed on items Council Review 16 explicitly filed as non-blocking follow-up tickets rather than its actual blocker list — a legitimate scope-discipline observation, though moot here since the sole approver explicitly authorized this exact scope (both "Full ADR-0045 compliance" and "Build it now" for capability gating) before the work began.
Recommendation: revise (small, targeted, prior to discovering the deeper defects below).

### SIS Domain Councilor

Ran the actual SQL against the real local schema rather than reasoning about it, and found two fatal defects nobody else caught: (1) faculty section-scoping in both `listStudentsWithFormationSummary` and `getStudentFormationRecord` queries `academy_registrations`/`section_id`/`instructor_person_id`, none of which exist — the real table/columns are `academy_course_section_registrations`/`course_section_id`/`primary_instructor_id`, confirmed against the live schema and against the correct pattern already used in `attendance/postgres-repository.ts` and `course-catalog/mutations.ts`. Any faculty-role actor calling either function gets a hard Postgres error, not an authorization decision — faculty scoping does not work at all, not just imperfectly. (2) `grantMinistryFormationReviewer`'s INSERT omits the NOT NULL `id`/`scope_type` columns and targets an `ON CONFLICT (person_id, tenant_id, role)` arbiter that doesn't match the real 5-column unique index on `academy_person_role_assignments` — reproduced via a rolled-back transaction against the live database, both failure modes confirmed. The entire reviewer-grant mechanism this round's ADR is built around cannot write to the database. Also independently confirmed the FK-restrict migration fails (third independent reproduction) and the registrar/academic_admin scoping defects (see Security and Privacy, below) via direct code reading, matching the other two councilors' live reproductions. Flagged explicitly: the mock DB's unconditional no-op on the role-assignment insert let all of this ship with 45/45 green tests, and called for at minimum one integration-style test against the real schema for the grant/revoke and section-scoping paths.
Recommendation: revise — "not a subtle scoping nuance; three of five findings are proven runtime failures against the real schema, reproduced directly via psql, not conjecture."

Student PWA nav-hiding is architecturally clean (single server fetch, no hydration-mismatch risk, UI-only — the destination page re-checks the capability server-side regardless). Independently built and applied the actual migration against a throwaway Postgres container and empirically confirmed the FK-restrict migration's constraint names don't match what Postgres generates (first of three independent reproductions). New `ministry_formation_reviewer` role value doesn't break any exhaustiveness check anywhere (grepped all 37 files referencing `AcademyRole`; no switch/Record pattern requires exhaustiveness in this codebase). Found that `ministry_formation_reviewer` was never wired into `endorserRoles`, so the grant-dialog copy falsely claims the role enables endorsement when it grants none. One inline SQL query added directly to the staff page instead of through a module function (minor, read-only). Noted a stray `.gitignore` line as "out of scope" — this was actually explicitly commissioned in a separate Council Review 16 housekeeping commit, not a defect; the councilor lacked that context.
Recommendation: revise.

### Security and Privacy Councilor

Wrote and ran a standalone probe script against the real (unmodified) `service.ts` with actual pastoral content, independently of any other councilor, and reproduced two critical privacy defects live: (1) `canSeePastoralNotes()` checks `hasReviewerAccess()` before the registrar exclusion, so a registrar granted `ministry_formation_reviewer` sees pastoral notes verbatim — reproduced with a real evaluation containing "CONFIDENTIAL: student disclosed a private family crisis," which appeared in full in the registrar-actor's response, directly contradicting ADR-0071 §4's explicit claim that the registrar cap holds regardless of reviewer status. Also reproduced live. Confirmed tenant isolation is otherwise sound in every new join, that `listStudentsWithFormationSummary` never selects pastoral notes by construction, that capability enforcement is present on all 9 routes including the two new grant/revoke-reviewer routes, and that nav-hiding is cosmetic-only (destination pages independently re-check server-side). Flagged the same misleading grant-dialog copy Architecture found.
Recommendation: revise — "two of the ADR's specific, named privacy guarantees are false in the shipped code, in the highest-stakes data category in this repo."

## Blockers

1. **[Confirmed by 3 independent live reproductions against real Postgres]** Migration `20260914030000_ministry_formation_advisor_assignments_fk_restrict.sql` drops foreign-key constraints by name, but the names it targets are not what Postgres actually generated when `20260914010000` ran (auto-generated composite-FK names are truncated to 63 bytes, differently per constraint). The migration fails outright on any fresh database. Owner: backend fix. Evidence required: regenerate this migration against the real, truncated constraint names (verify by actually applying `20260914010000` locally and querying `pg_constraint`, not by reasoning about Postgres's truncation algorithm), or give the FKs explicit short names via a new migration first.
2. **[Confirmed by live reproduction against real Postgres]** `grantMinistryFormationReviewer`'s INSERT into `academy_person_role_assignments` omits the NOT NULL `id`/`scope_type` columns and targets an `ON CONFLICT` arbiter that doesn't match the table's real unique index — the statement fails against the actual schema every time. The reviewer-grant mechanism cannot write to the database at all. Owner: backend fix. Evidence required: correct the INSERT to supply all required columns and target the real unique index (or use an existence check instead of `ON CONFLICT`), verified by actually running it against the local database, not just the mock.
3. **[Confirmed by live reproduction against real Postgres]** Faculty section-scoping in both `listStudentsWithFormationSummary` and `getStudentFormationRecord` queries `academy_registrations`/`section_id`/`instructor_person_id`, none of which exist in the real schema — the correct names, already used correctly elsewhere in this codebase, are `academy_course_section_registrations`/`course_section_id`/`primary_instructor_id`. Any faculty actor calling either function gets a hard database error. Owner: backend fix. Evidence required: correct the join to match the schema, verified against the real local database.
4. **[Confirmed by live reproduction with real pastoral content, independently found by 2 more councilors]** `canSeePastoralNotes()` checks `hasReviewerAccess()` (institution_admin or `ministry_formation_reviewer`) before the registrar exclusion, so a registrar granted the reviewer role sees pastoral notes, contradicting ADR-0071's explicit design. Owner: backend fix. Evidence required: reorder the check so the registrar cap is evaluated independently of and cannot be overridden by reviewer access; add a registrar+reviewer regression test using real pastoral content and `doesNotMatch`.
5. **[Confirmed by live reproduction, independently found by 2 more councilors]** `getStudentFormationRecord`'s staff-scoping block has no `else`/deny branch for a formation-viewer role that isn't reviewer/faculty/advisor/registrar — `academic_admin` alone gets fully unscoped tenant-wide read access to any student's record, contradicting ADR-0071's explicit claim that academic_admin needs the reviewer role explicitly granted like anyone else. The sibling function `listStudentsWithFormationSummary` already has the correct `else { throw }` pattern. Owner: backend fix. Evidence required: add the matching deny-fallback; add an academic_admin-only rejection test for `getStudentFormationRecord` specifically.
6. **[Confirmed by 2 councilors]** `ministry_formation_reviewer` was never added to `endorserRoles`, so the grant-dialog UI copy ("They will be able to endorse practicum sessions, milestones, and evaluations") is false — the role grants zero endorsement capability, only pastoral-notes visibility. Owner: frontend fix (copy correction — do not expand `endorserRoles`, that would be a scope change beyond what was asked for; fix the description to state the real effect).

## Decision

The council decision is `revise`.

Every one of the five blockers has a small, mechanical, verifiable fix — this is not an architectural rejection. But the volume and severity of what three independent councilors found by actually running the code against a real database, versus what 45/45 mock-based tests reported, is the headline finding of this review: the mock-DB testing pattern this module has used since its original implementation has a real blind spot for schema-shape errors (wrong table names, wrong column names, wrong constraint names), and that blind spot let three separate runtime-breaking defects ship as "tested." The fix pass for this round must verify against the actual local database, not just re-run the mock-based suite and call it done.
